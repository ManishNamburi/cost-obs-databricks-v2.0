# cost-obs v2.1 — Formal Spec

**Status:** In development
**Baseline:** v2.0 (2.0 mirror at `smathews13/cost-obs-databricks-v2.0`)
**Anchor commit:** `a21965e` on `sam-mathews_data/cost-obs-app-v2` (parity with v1 1.1 restored)

This document captures the scope, decisions, and open technical questions for the 2.1 release. It is the source of truth for anyone picking this work up mid-stream.

---

## 1. Release Themes

Three headline capabilities, plus deployment plumbing:

1. **Static Genie cost dashboard tab** — customer-facing, reads `system.billing.*`.
2. **DAB-managed Genie space** — conversational Q&A over the customer's cost data model, seeded through the setup job.
3. **AI/ML → AI Gateway merge** — the AI/ML tab is retired and its content folds into the existing AI Gateway tab.
4. **App-wide conversational surface** — AI Gateway-backed narrative features (anomaly explanations, spend spike commentary, "what changed since last week") reachable from anywhere in the app.
5. **Two deployment patterns** — fresh install and 1.1 → 2.1 migration.

## 3. Governing Principle: DAB owns everything

**All infrastructure — the Databricks App, the SQL warehouse binding, the Lakebase project + endpoint, the Genie space, the setup job, permissions, and env-var injection — is declared and managed inside the DAB (`bundle/`).**

Nothing critical is provisioned outside the bundle. `databricks bundle deploy` is the single source of truth for creating and updating infrastructure. The only work that happens outside `bundle deploy` is the setup job's runtime steps (grants that the TF provider can't issue at plan time; migration-mode DBFS → Lakebase state moves; Genie-space instructions seeding). All of these are triggered by `bundle run cost_obs_setup`, not by manual CLI calls.

This applies to the Lakebase database specifically: **Lakebase project + endpoint are DAB resources** (defined per-target in `bundle/resources/lakebase.yml`; the `CAN_USE` grants that panic in TF v1.117.0 live in the setup job at runtime, not the resource definition). See §4.5 for the fresh + migration deployment flows.

## 4. Architecture

### 4.1 Static Genie cost tab

**Backend:** `app/backend/routers/genie_cost.py` (added in this session, registered at `/api/genie-cost`).

- **Endpoint:** `GET /api/genie-cost/dashboard-bundle` — returns `{summary, workspaces, timeseries, surface_breakdown}`.
- **Diagnostics endpoint:** `GET /api/genie-cost/diagnostics` — dumps distinct `(sku_name, usage_type, billing_origin_product)` combos over the last 90 days for anything matching `%GENIE%` or `%AI_BI%`. Field engineers use this to validate the sub-surface and free-tier mappings against real customer data.
- **Source tables:** `system.billing.usage`, `system.billing.list_prices`, `system.access.workspaces_latest`.
- **Sub-surface detection:** `sku_name ILIKE '%GENIE_CODE%'` / `%GENIE_ONE%'` / `%GENIE_AGENT%'` (defaults; centralized in `_SURFACE_CASE_SQL`; forward-compatible if Databricks adds new SKU strings).
- **Free-tier detection:** `usage_type = 'BILLABLE'` → charged; `NON_BILLABLE` / `RELATED` → free-tier; anything else → excluded (centralized in `_CHARGE_CLASS_CASE_SQL`).
- **"Other Genie" bucket:** if the residual (total minus the three known sub-surfaces) is non-zero, it surfaces as a fourth surface row — a signal to open the Diagnostics panel.

**Frontend:** `app/frontend/src/components/GenieCostView.tsx` (pending).

- KPI cards: Total Genie USD, Charged, Free-Tier, Genie % of DBX Spend.
- Sub-surface breakdown table with Code / One / Agents / Other columns.
- Per-workspace table (sorted by `total_usd desc`).
- Timeseries chart: daily Genie spend split by charge class or sub-surface.
- Diagnostics panel behind Settings → Diagnostics → Genie (or an inline "?" affordance).

**App.tsx wiring:** New `"genie"` value on `ViewTab`; nav button between "AI Gateway" and "Apps" (or wherever fits the tab order).

### 4.2 DAB-managed Genie space

**Bundle resource:** `bundle/resources/genie.yml` (pending) — declares the Genie space with `Can run` for the app SP. `GENIE_SPACE_ID` injected into the app runtime env from the resource binding.

**Curated content:** `setup/notebooks/03_seed_genie.py` (stub exists; needs full content).

- **Data sources:** four-table spine per the AI Gateway/Genie package:
  - `system.billing.usage`
  - `system.billing.list_prices`
  - `system.billing.account_prices`
  - `system.access.workspaces_latest`
- **Instructions:** time-aware join between usage and price tables; use `usage_date` for time-grain; map AI spend to documented billing products; distinguish list price from discounted price; treat unsupported questions as unsupported; avoid hallucinated interpretations of `usage_quantity`; clarify that cloud VM costs are not available in the space.
- **Sample questions:** total spend this month; top workspaces by spend this quarter; product with highest spend; top 10 users by spend; cost of model serving this month; AI product cost trend over last 90 days.
- **Guardrails:** always expose generated SQL when available; expose result table attachment; label unsupported questions; note when an answer is list-price-only.

### 4.3 AI/ML → AI Gateway merge

- **Backend:** `aiml.py` content folds into `ai_gateway.py`. Router prefix stays `/api/ai-gateway`; `/api/aiml` endpoints become aliases or redirects for one release, then retired in 2.2.
- **Frontend:** `AIMLCostCenter.tsx` content merges into `AIGatewayView.tsx`. `AIMLCostCenter.tsx` is deleted. Tab labeled "AI Gateway" throughout.
- **`ViewTab`:** drop `"aiml"`; keep `"ai-gateway"`.

### 4.4 App-wide conversational surface

**Two components:**

1. **`genie_service` (backend):** wraps the Genie Agents API. Starts a conversation per user session, polls message status (1–5s exponential backoff), fetches generated SQL + attachments + result rows. Never reuses conversations across sessions.
2. **`ai_gateway_service` (backend):** thin OpenAI-compatible client against `/ai-gateway/v1`. Tags every request: `project=cost-obs`, `feature=<anomaly_summary|spend_spike|weekly_narrative|...>`, `surface=app`, `environment=<target>`, `workspace_scope=<single|multi>`.
3. **`cost_intelligence_router` (backend):** decides Genie vs AI Gateway per the routing policy in the AI Gateway package (cost questions → Genie; narrative/explain → AI Gateway; mixed → Genie first, AI Gateway summarizes).

**Frontend surface:** floating chat widget (bottom-right, dismissable) or slide-out drawer; specific placement TBD in design pass. **Not to be confused with the Genie *tab*, which is static.**

**Anomaly summary endpoint:** existing "explain this anomaly" affordance in `SpendAnomalies.tsx` gets wired to `ai_gateway_service` with `feature=anomaly_summary`.

### 4.5 Deployment patterns

**Fresh install path** (no prior cost-obs deployment):

```bash
databricks bundle deploy -t <target>
databricks bundle run cost_obs_setup -t <target>
```

Setup job runs all six phases: `validate → bootstrap_lakebase → migrate_delta → seed_genie → setup_usage_policy → verify`.

**1.1 → 2.1 migration path** (existing 1.1 customer):

Recommended default: **in-place upgrade**. The setup job auto-detects existing 1.1 state and:

1. Preserves the existing catalog/schema and MV tables (`daily_usage_summary`, `daily_product_breakdown`, `daily_workspace_breakdown`, `sql_tool_attribution`, `daily_query_stats`, `dbsql_cost_per_query`, `daily_tag_summary`, `daily_apps_summary`).
2. Provisions Lakebase project + endpoint (new in 2.x).
3. Migrates 1.1 app state (permissions, alerts, config, workspace_config) from Delta / DBFS → Lakebase via `02b_migrate_delta.py`.
4. Seeds the Genie space (`03_seed_genie.py`).
5. Skips MV rebuild (existing tables are still valid; nightly refresh keeps them fresh).

**Detection:** setup job's `01_validate_prereqs.py` probes for `daily_usage_summary` existence and prior `setup_state` rows. Presence → migration mode. Absence → fresh mode. Operator can force via a `DEPLOYMENT_MODE=fresh|migrate` bundle variable.

**Force-fresh:** operator can force full rebuild by setting `DEPLOYMENT_MODE=fresh` — useful for catalog moves or when a customer wants to start over.

### 4.6 Bundle changes required

**New resources:**
- `bundle/resources/genie.yml` — Genie space (with `Can run` for app SP)
- `bundle/resources/lakebase.yml` (re-enable — currently `.disabled` due to TF provider CAN_USE panic; fix is per-target definitions)

**New / updated bundle variables:**

- `AI_GATEWAY_BASE_URL`
- `AI_GATEWAY_MODEL`
- `AI_GATEWAY_REQUEST_TAGS_DEFAULT`
- `GENIE_SPACE_ID` (already exists; will be populated by the Genie resource binding)

**app.yaml env injection:**

- `AI_GATEWAY_BASE_URL` static
- `AI_GATEWAY_MODEL` static
- `AI_GATEWAY_REQUEST_TAGS_DEFAULT` static

## 5. Technical Decisions (all confirmed 2026-07-12)

All ten open questions from the earlier draft of this document were answered by the product owner in-session. This section captures the final decisions verbatim — all subsequent implementation must follow these.

### 5.1 Genie SKU sub-surface mapping — provisional heuristic

**Decision:** yes as a provisional heuristic, not a contractual dependency.

Classify with:
- `sku_name ILIKE '%GENIE_CODE%'` → `charged_usd__genie_code`
- `sku_name ILIKE '%GENIE_ONE%'` → `charged_usd__genie_one`
- `sku_name ILIKE '%GENIE_AGENTS%'` → `charged_usd__genie_agents`

Additional bucket:
- `charged_usd__genie_unknown` for anything charged that doesn't match one of the three patterns.

The `/api/genie-cost/diagnostics` endpoint shows top raw `sku_name` values + counts so we can validate against real customer billing data after deploy. **Rule:** code must be forward-compatible; unknowns must not break the dashboard.

### 5.2 Free-tier attribution — reporting convention

**Decision:** use this convention for v1:

- `usage_type = 'BILLABLE'` → charged
- `usage_type = 'NON_BILLABLE'` → free tier
- `usage_type = 'RELATED'` → free tier
- Anything else → **exclude** from Genie charged/free-tier buckets AND surface in Diagnostics

**Guardrail:** add an `other_usage_type_usd` diagnostics output so new/unknown `usage_type` values are visible if they appear.

### 5.3 Genie Agents API auth — SP token

**Decision:** service principal token for v1.

Databricks Apps grant the app SP permissions on the selected Genie Agent resource; the Genie API docs explicitly recommend SP auth when browser-based user auth isn't available. Build `genie_service` using the app SP. Defer user OBO / RLS-style behavior to a later phase.

### 5.4 AI Gateway model service — shared default with override

**Decision:** shared default with override via `AI_GATEWAY_MODEL`.

Unity AI Gateway is designed around centrally governed model services; Databricks-hosted models are available as ready-to-use services so a sane shared default is reasonable for first release.

Env vars supported:
- `AI_GATEWAY_BASE_URL`
- `AI_GATEWAY_MODEL` — if unset, use the app's documented shared default model service

Keep override behavior explicit and documented.

### 5.5 Anomaly summary prompt — KPI-only

**Decision:** KPI-only for first release.

Prompt contents allowed:
- headline metric
- prior-period delta
- top drivers
- affected account / workspace / product labels
- anomaly score / threshold context if available

Do **not** send raw row dumps in v1. Detailed-mode prompting can come later behind a feature flag.

### 5.6 Lakebase migration ownership — app SP, setup-job runtime

**Decision:** app service principal owns the Lakebase project; grants happen at **setup-job runtime**, not Terraform plan time.

Keep migration-mode provisioning app-driven; put grant / repair logic in setup-job execution. Do not make deploy-time infrastructure depend on account-admin or platform-admin credentials.

### 5.7 `01353d9`-era WorkspaceClient fix — leave as-is

**Decision:** yes, leave alone.

Do not refactor or remove the `01353d9` (`f6c366d`) work as part of the AI Gateway / Genie effort. Treat it as unrelated stabilization already accepted into 2.1.

### 5.8 AI Gateway derived table — manual account-admin prerequisite

**Decision:** documented manual account-admin prerequisite.

`system.ai_gateway.usage` is only queryable by account admins; the built-in AI Gateway dashboard creation is also account-admin gated; cost observability depends on account-level billing system tables being enabled.

Implementation:
- Do **not** require account-admin credentials inside `bundle deploy`.
- Document the prerequisite clearly (`docs/AI_GATEWAY_SETUP.md`).
- App setup / diagnostics verifies the derived table exists and is readable.
- If missing, fail clearly with instructions instead of attempting privileged creation automatically.

### 5.9 Genie space count — one shared space

**Decision:** one shared Genie space for v1.

App access is scoped to the selected Genie Agent, so one curated shared space keeps deployment and permissions simpler for first release. Use one `GENIE_SPACE_ID`. No per-catalog or per-tenant cloning in v1. Revisit only if data isolation or curation quality forces a split.

### 5.10 Header badge — stay `v2.1`

**Decision:** stay `v2.1` through the 2.1.x series.

Do not change header badge text for this workstream. Reserve `v2.1.1` for an explicit versioning decision later.

### Final build defaults (single reference for coding agents)

- Genie dashboard tab: static reporting tab, not chat
- Genie Q&A: separate DAB-managed Genie space
- Genie auth: app service principal
- AI Gateway model: shared default plus env override
- Anomaly summaries: KPI-only
- Lakebase migration owner: app service principal
- AI Gateway derived table: manual documented account-admin prerequisite
- Genie space count: one shared space
- UI badge: stay `v2.1`

## 7. Non-Goals for 2.1

Explicit non-goals from the AI Gateway/Genie package:

- **Do not turn the Genie tab into a chat surface.** The tab is static reporting.
- **Do not reimplement Genie through AI Gateway.** They serve different governance planes.
- **Do not position 2.1 as a full FinOps copilot.** Query-level warehouse cost + cloud VM cost + detailed optimization advice remain out of scope for the curated Genie space.
- **Do not silently hallucinate unsupported cost answers.** Reject or reframe unsupported questions.

Additional 2.1 non-goals:

- **RLS via user OBO on the Genie space.** Deferred to 2.2 unless prioritized.
- **Detailed anomaly summaries with raw row context.** Ship KPI-only first (see §5.5).
- **Fanned-out Genie spaces per catalog.** One shared space (see §5.9).

## 8. Acceptance criteria

The 2.1 release is done when:

- Genie cost tab loads for a customer deployment, shows the required metrics, and gracefully handles missing sub-surface splits (either populated or clearly labeled zero with Diagnostics available).
- DAB Genie space is provisioned via `databricks bundle deploy` and seeded via `bundle run cost_obs_setup`.
- Conversational Q&A works over the four-table spine — sample questions from §4.2 return valid results.
- The AI/ML tab is gone; AI Gateway tab absorbs its content with no regression on the AI/ML-specific views.
- Anomaly explanation feature routes through AI Gateway with `project=cost-obs, feature=anomaly_summary` tags visible in `system.ai_gateway.usage` (via the derived table).
- Fresh install works end-to-end from a clean workspace.
- 1.1 → 2.1 migration preserves existing MVs, provisions Lakebase, migrates state, and doesn't reset any customer configuration.
- Header badge reads `v2.1`.
- Palette / purple / WCAG / Recharts-flicker audits all pass.
- README carries a 2.1 release notes section with a "What's new," "Upgrading from 2.0," and at-a-glance changelog table.
